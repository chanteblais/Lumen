# Coherence — Session Brief

Loaded automatically at the start of every Claude session in this repo (root `CLAUDE.md`; worktrees carry it too). Deliberately short; the detailed docs in `docs/` are read on demand. Same shape as the Glåüm and All Hands briefs, so sessions behave the same way across projects.

**Coherence** (the product, formerly **Lumen**; the companion character is **Lumi**, she/her) — an AI companion for task initiation, momentum, re-entry and body doubling. **Not a task manager.**

**Before substantial product/UX work** (features, navigation, AI or Lumi behaviour, prioritisation, notifications, rewards, visual design, motion, onboarding, memory), **read `PROJECT-CANON.md` and the canonical docs it points to for that work.** The canon is the intended product; code is the current one. When they disagree, surface it and don't silently pick one. Only decisions in `docs/living/decisions.md` are requirements; ideas and open questions are not.

**The question that overrides everything:** does this reduce the user's executive-function burden, or accidentally create more of it? Ask it before adding any field, control, count, or setting.

## Conventions
- `src/core` is framework-free (no `next`/`react` imports; ESLint enforces). Domain logic and AI assembly live there and are unit-tested.
- The model **reads** state via the context block and **writes** only via tools. Every tool write appends an `events` row. Never parse prose for state. The *why* behind this layer, and the seams to keep as it grows (conversation ≠ state, explicit ≠ inferred, priority ≠ attention, spaces ≠ data silos…), is `docs/product/ai-and-information-architecture.md` (§57 seams, §61 review questions).
- Greeting and focus check-ins are deterministic (no LLM call). Lumi speaks unprompted only for check-ins.
- Store facts and events; derive judgements (stale, avoided, gap) at read time. Never persist derived flags.
- **Understanding layer is first-class:** beliefs (`memory_notes`) carry confidence + evidence; the model proposes belief ops, `core/domain/memory.ts` applies them with guardrails; outcomes (sessions, completions) are the feedback signal. The user never rates or tags anything.
- Persona prompt (`src/core/ai/persona.ts`) + tool descriptions are the cached prefix — keep them byte-stable; volatile context goes after. They *implement* Lumi's behaviour; its source is `docs/philosophy/lumi.md`. Don't rely on behaviour that only one model happens to produce: Lumi's model is under evaluation (`docs/product/lumi-model-strategy.md`).
- Clerk is imported only in `src/lib/auth.ts` (server: `requireUser()`, `googleAccessToken()`), `src/lib/auth-ui.tsx` (provider + sign-in/up/account controls), `src/lib/auth-mail.tsx` (the Connect Google chip) and the sign-in/sign-up pages. Internal `users.id` everywhere else; mail reaches `src/core` only as an `EmailReader` (`src/lib/email.ts`).

## Working conventions — standing tasks (every session)
- **Branching (start here):** before your first edit, create your own branch — `type/slug` (`feat/` `fix/` `ux/` `docs/` `chore/`; milestones `feat/m<N>-<slug>`) or `session/YYYY-MM-DD-<topic>` if the scope isn't clear yet. `main` = deployable (push = prod deploy). Verify (`npm run check` — typegen + tsc, eslint incl. the `src/core` import guard, vitest, route-auth audit — plus a local click-through), run the **docs audit** (below), merge `--no-ff`, delete the branch. Tiny tweaks (log/doc one-liners) may go straight to `main` with `COHERENCE_ALLOW_MAIN=1`. Claude may push `main` once Chanté has confirmed the change ("looks good" / "merge it" covers the deploy) — never unconfirmed work — and only after the docs audit has passed on everything that would ride along. A pushed branch may also go up as a PR (CI + preview + the desktop app's CI watch); merge it with a merge commit, never squash. Full rules: `docs/branching.md`.
- **Parallel sessions:** one checkout = one git-active session. If `git branch --show-current` shows a branch you didn't create, someone else is here — take your own `git worktree` (the EnterWorktree tool) instead of branching in place. Never `git add -A` in the shared checkout — stage explicit paths. Never bare `git stash` (the stack is shared). Details: `docs/branching.md` → Parallel sessions.
- **Review server:** once a change is implemented, **start the dev server and leave it running** so Chanté can view it (`npm run dev -- -p 3005`, background). **Ports 3000–3004 belong to other projects on this machine — never start or stop anything on them.** With the URL, give a **review checklist**: each page to visit and the specific thing to look for there (incl. any precondition, like an unapplied migration), plus **which branch/checkout the server serves** — a dev server serves the live working tree of the checkout it started in, so switching branches there switches what the browser shows. Only stop servers Claude started; once the change is merged to `main`, stop the review server.
- **Port etiquette:** before starting any server, check who's on the port and *what checkout it serves*: `PID=$(lsof -nP -iTCP:3005 -sTCP:LISTEN -t)` then `lsof -a -p $PID -d cwd`. **Never kill a server you didn't start.** If it already serves the checkout + branch you need, reuse it. Otherwise take the next free port (3006, 3007, …) from **your own worktree**. Never run two dev servers from one checkout — they share `.next` and corrupt each other. Always say which port serves which branch.
- **Print migrations:** whenever a migration is created or changed, print the full SQL verbatim in the final chat summary with a one-line destructive-or-not note. Chanté reviews and applies migrations herself and must never switch branches just to read one.
- **Docs before commit:** before **every** commit, sweep the docs and fold the change in — `docs/domain.md` (tables + migrations reference), `docs/features.md`, `docs/architecture.md` (API routes, conventions), `docs/design-system.md` for anything visual, the relevant spec (e.g. `docs/today.md`), `docs/decisions.md` when a decision moved — so docs land in the **same commit** as the code they describe. A commit that changes schema, API or UX with untouched docs is incomplete.
- **Docs audit before merge / push (every time, no exceptions):** the per-commit sweep catches what one commit changed; the audit catches what the *branch* changed. It is the last step before any `--no-ff` merge, PR merge or push of `main`, after `npm run check` and the click-through. Run `git diff main...HEAD --stat` (or `origin/main..main` before a push) and, for every changed file, ask which doc describes it — schema → `docs/domain.md` · routes, conventions, the AI layer → `docs/architecture.md` · a page or feature → `docs/features.md` · anything visual → `docs/design-system.md` · a new sheet, painting or mockup, or a change to how Lumi looks or moves → `docs/art-direction.md` · a new page or nav item, a painted place, or a feature placed in a space → `docs/product/spaces.md` and `PROJECT-CANON.md` → The spaces · a page with a spec → that spec (`docs/today.md`…) · a decision that moved → `docs/decisions.md` (and `docs/living/decisions.md` if it changes how the product behaves or why) · behaviour that now differs from the canon (`PROJECT-CANON.md`) → raise it with Chanté, never silently · anything the user is asked to keep → `docs/ef-burden-log.md` · a new working rule → `CLAUDE.md` / `docs/branching.md`. Read the relevant passage, not just the filename: a doc that still describes the old behaviour is stale even though it mentions the feature. Anything stale is fixed **on the branch, before the merge** (its own `docs: …` commit is fine), never after. The final summary names the docs checked and the ones touched, or says "docs audited, nothing stale". A merge or push without the audit is not ready — including tiny `COHERENCE_ALLOW_MAIN=1` tweaks, which get the same question in miniature.
- **Animation work (Lumi's sheets in `art/`, the cut scripts, the companion's loops):** read `docs/animation-pipeline.md` **first** and follow its session-start checklist (it sends you to `docs/art-direction.md` for the tier and the bets); before finishing, do its session-end steps — fill the ledger row, land or re-rank one efficiency-backlog move, fix what the doc got wrong. Chanté wants many animations; every animation session leaves the pipeline faster than it found it, and the doc is where that compounds. It goes in the same commit as the animation.
- **EF-burden log:** during **any** iteration, when code or copy asks the user to set, keep current, rate, confirm or remember something, or shows a count of undone things, **append a row to `docs/ef-burden-log.md`** before finishing (log it, then decide: `accepted` / `derived` / `removed` / `open`). Prefer derived-from-behaviour over asked. This is the dogfood ledger for the one question.
- **Logs are append-only, newest first:** `docs/qa-log.md` per sweep (Fixed · Known and deliberate · Open · Highest-value manual tests — read "known and deliberate" before re-reporting), `docs/ux-review-log.md` per pass (severity / effort / status; fixes only once Chanté agrees), `docs/voice-eval-log.md` per persona run, `docs/decisions.md` per changed decision.
