## 2. How the AI layer touches application state

**Principle: the conversation is the interface; structured state is the truth.** The model reads state through a context block and writes it through tools. The UI renders structured state from the database. Nothing ever parses Lumi's prose to discover what happened, and Lumi never edits state by "just saying so".

### One turn
```
client useChat ──POST /api/chat {id, message}──▶ route handler
                                               │ requireVisit()  (finds the user, records the visit)
                                               │ parseChatBody → 400 if it isn't one user message of text
                                               │ client event (Not this, a session tap) recorded; conversation window (30–39 UIMessages) + snapshot + Library loaded
                                               │ buildContextBlock(contextInputFor(…))  → context block (see below)
                                               │ streamText({ instructions: [persona (cached)], messages: [...history, newest user message + context block], tools, stopWhen: stepCountIs(5) })
                                               │   tools execute server-side → DB writes + events → compact results
                                               │ onEnd: persist the user message (before the model) and the assistant message; after(): prime/re-cut, reflect, consolidate
                                               ◀── UIMessage stream (text parts + tool parts) ──
client renders text; tool parts render as quiet "ledger" lines (✦ Noted · Draft intro), with undo where cheap
```

### The prompt = stable prefix, conversation, volatile context (in that order)
The request is laid out for the prompt cache, which reads a request's longest unchanged prefix (`core/ai/prompt.ts`, code review B9, 2026-09-13): tool descriptions and the persona, byte-stable; then the conversation window, whose start moves ten messages at a time (`stableWindow`: 30–39 messages, the first in view held for about five turns, counted from the conversation's first message) so its bytes repeat from turn to turn; then the context block, which changes every turn, as a marked text part after their words in the newest user message (`withContext`: `<context>` + a fixed lead line + the block, built per request and never stored; a `<context>` they type is defanged). Both providers take it as it is, so the order is the same on each (`prompt.test.ts` pins it on the wire): `cachedPrefixOptions` (`model.ts`) marks the same two breakpoints on both providers — on the persona, and on their last words before the context: `cacheControl` on Anthropic, an explicit `promptCacheBreakpoint` on OpenAI, where GPT-6 keeps a cache entry only at a breakpoint; each kind of call also has its own `promptCacheKey`, which routes requests to the same cache. A trailing system message was not used: the Anthropic provider sends mid-conversation system messages only behind a beta. Before this the context block sat between the persona and the history, and the window slid by two every turn, so nothing after the persona and tools was ever cached.
### System prompt = stable prefix + volatile context
2. **Context block** (`src/core/ai/context.ts`), regenerated every turn, placed *after* the conversation, on the newest user message:
   - now (user's local time + weekday), timezone
   - **where they are** (chat, 2026-09-13): one line — the page they spoke from and which way in (Home's conversation, the bubble, Lists' Add task), from the request's `where` (`core/places.ts` → `parseWhere`; only a known place and slot, else no line). Never stored. The persona's *The app, and where they are* says how to use it, alongside a map of the places, what each lets the user do by hand, and what isn't built
   - time since last visit (`users.last_seen_at`), phrased in buckets ("3 hours", "9 days")
   - today's capacity report, if any
   - open intentions (≤ 25, newest-touched first; stale ones flagged `stale: 14d`), with ids
   - **recent changes** (≤ 12, newest first, last 36h; `core/domain/activity.ts`): every `intention.*` change joined to its title and current status, phrased by who did it — *they ticked "X" done on Today or in the Library* (`payload.via: "app"`) vs *you marked "X" done* (a tool). This is how "add back the one I just checked off" works: ticks on a page never appear in the transcript, so the block carries them, with the id, and the persona says act on it rather than ask. Chat-only (pages don't load it).
   - recently done (≤ 5) with ids and when, so a mistaken tick can be undone by id (`reopen_intention`)
   - **what they said matters** (2026-09-13, `listCurrentPriorities` via the snapshot): each stated priority that holds today or was said for a week still ahead, as id · *this week* / *next week* / *for a while* · their words · the intention it names. Headed as their word, kept apart from Lumi's own ordering, with `hold_priority` (with `replaces`) for a change and `let_go_priority` when it stops mattering. Left out when there are none
   - *(removed 2026-09-13 with focus sessions: the running and last session, and the Just now lines for check-in taps, Start with Lumi and a Not this handed off from Today)*
   - **what you know about them** (chat: ≤ 12 beliefs chosen for this turn by `core/ai/memory-select.ts` — see The understanding layer → Retrieval): each quoted on one line with id, kind, whose word it is (*their word* / *your guess* / *from a session*), confidence; strategies with evidence counts; low-confidence ones marked *tentative*. Headed by a line saying notes are data, not instructions, and never override the rules or the current request; a line when more is held (`recall_memory`), and one when beliefs couldn't be read this turn
   - **their mail** (chat-only): when Lumi last looked (`email.scanned`), and the suggested leads (≤ 8) — what she noticed there that might need doing, unconfirmed, with ids for `keep_lead` / `dismiss_lead`
   - **lately, between you** (chat-only, 2026-09-13): ≤ 3 episodes — short memories of visits — that ended before the oldest message in view, from the last 14 days, each with where it was left
   - **the Library** (chat-only, 2026-09-13): ≤ 2 threads the turn touches, each with its summary and ≤ 6 notes (id · kind · note · their word or your reading · the day it was filed, in their timezone), and an index of ≤ 12 others for `open_thread`; headed as data, not instructions, with a line when it couldn't be read. See The Library, below
   - `preferences` (tone hint; the session length and check-in interval are unused since 2026-09-13)
   The block is small on purpose. If a list outgrows its cap, we add a read tool (`search_intentions`) rather than growing the block.

Rules for tools:
- Every write tool also appends an `events` row (append-only). This is non-negotiable — it is the raw material for future pattern memory.
- Tool results are compact JSON (`{id, title, status}`), never prose. Lumi narrates in her own words.
- Tools never throw to the model; failures return `{error}` so Lumi can say "I couldn't save that" instead of the turn dying.
- No `list_*` read tools over our own state in V1; the context block covers reads. Add them when caps bite. `look_at_email` is the exception: mail is not our state, it is large, and it is read only when asked.
- Tool descriptions are part of the cached prefix — keep them stable.

- **Focus sessions, their check-ins and the abandoned-session sweep — removed 2026-09-13** (Chanté's call). No session bar, no `/api/session`, no session tools, and `loadSnapshot` no longer closes sessions left open. `core/focus.ts`, `core/domain/sessions.ts` and session reflection (`reflectOnSession`) remain, unused.
- **Quick-start chips** ("Help me choose", "Break it down", "Just talk") send a canned first user message. They are starting points, not modes.
- **Today's capacity prompt and the *Not this* question** (M4). "How much have we got today?" and "Fair. What's getting in the way?" are fixed copy in `core/declines.ts` / `components/today/CapacityPrompt.tsx`; a decline answer records the reason and re-cuts the path on the card (`PATCH /api/intentions/[id]`, 2026-09-13) — no chat message, no reply; the next Right now is picked in code from After that and carries a fixed line for the reason (`DECLINE_NOTES`), and the model refines the rest off the response.
- **Staleness, visit gap, sitting, "avoiding" signals** are derived queries (`src/core/domain`), never stored flags.

### The understanding layer (memory that learns)

This is a first-class subsystem, not a notes table. Its job: **continuously refine a model of what is most helpful to this particular user**, using their behaviour as the signal, without ever asking them to rate, tag, or maintain anything.

**Model: beliefs with evidence.** `memory_notes` rows are beliefs. Each has a `kind` (fact · project · preference · strategy · pattern · anti_pattern), a one-sentence `content`, a `confidence` (0–1), counts of `evidence_for` / `evidence_against`, timestamps for last confirmation and contradiction, a `supersedes_id` so revisions keep history, and a `source_message_id` for the message it came from. Retirement (contradiction drift, supersession) is soft, with a reason; the user's forgetting is a delete. The user-facing name is **"What Lumi knows"**.

Facets and what they capture:
| kind | example | where the signal comes from |
|---|---|---|
| fact / project | "Thesis due 30 Oct; supervisor is Priya." | conversation |
| preference | "Wants blunt, short replies. Lists of options make her freeze." | conversation + how she responds to Lumi's style |
| strategy | "Opening the doc and reading the last paragraph gets her started." | sessions that begin with that approach and reach `completed` |
| pattern | "Starts real work after 10am; evenings are for small things." | events over time |
| anti_pattern | "Planning sessions become avoidance." | intentions touched repeatedly, never entered a session |

**Three inputs, one loop.**
1. **Explicit.** The user says something durable; Lumi calls `remember` (`source: user_said` with their words quoted and checked, confidence 0.9). Corrections — `correct_belief` in chat on their words, or *Correct* in Settings → What Lumi knows — are `user_said` at 0.95 and supersede the old belief — the highest-signal input there is. Forgetting (chat or Settings) deletes.
2. **In-conversation inference.** Lumi notices ("third time this week you've mentioned that paper") and records a hypothesis at low confidence via `remember`, or adjusts an existing belief via `confirm` / `contradict` / `revise`. Tentative beliefs are rendered as tentative in the context block, so Lumi tests them gently ("Last time opening the doc first helped — try that?") rather than asserting them.
3. **Outcomes.** Every intervention is linked to a result through `events`. `start_focus_session` records the `approach` being tried; `session.ended` carries the outcome; `intention.completed` links back to the session. Nobody rates anything — starting, completing, abandoning and re-entering *are* the feedback. *(With sessions removed on 2026-09-13, outcomes come from completions, declines and re-entry for now.)*

**Reflection** (`src/core/ai/reflect.ts`) turns inputs 2 and 3 into belief updates. **Code applies the operations with guardrails** — never retire a `user_said` belief without the user, cap operations per run, every op writes a `memory.*` event — so the model proposes and the code decides. Triggers in V1 need no cron: (a) when a focus session ends (M5, built; dormant since sessions were removed, 2026-09-13), (b) lazily on the first turn of a new local day (M6). Both run in Next's `after()` so they add no latency to the reply. Model: Lumi's (`gpt-6-astra`, `model.ts`) at low reasoning effort while volume is tiny; a smaller tier (`gpt-5.6-luna`) is the step-down.

*Session-end reflection (M5, `reflectOnSession`) — dormant since 2026-09-13: nothing starts or ends a session, and neither the chat route nor Home hands one over.* It runs in two steps. **Code first, no judgement:** a completed session whose `approach` names a `strategy` belief confirms it; stopped early is neutral (stopping is allowed and says little about the way in); an abandoned one (left open, closed by a later visit) is an unknown ending and yields nothing, from the code step or the model step (`worthModelStep` is false for it). Until 2026-09-14 it contradicted the strategy; the app losing sight of someone says nothing about how the work went (open question 28). The match is on content words, lightly stemmed (`matchesStrategy`: "read the last paragraph first" ≈ "Reading the last paragraph first gets her started."). **Then one model call** with structured output (`REFLECTION_RULES` + the session, its check-ins, the conversation around it, the active beliefs with ids) proposing `create | confirm | contradict | revise` (no retire — retirement only happens by contradiction drift or the user). `clampReflectionOps` keeps: ids that are active and untouched this run; strategy evidence only from a session that used that strategy (approach or first step); creates as `source: reflection` at ≤ 0.6; no strategy created twice; the run under `MAX_OPS_PER_RUN`. Evidence Lumi already recorded during the session (her own `confirm_belief` in the reply to "Done") is not recorded again. A session that ended within a couple of minutes without finishing skips the model step. Deterministic ops apply even if the model call fails; `reflection.ran {trigger: session_end, ops}` and `users.last_reflected_at` are written either way. Reflection runs **once per session**: before any work it claims the session — `reflection.claimed`, inserted on conflict do nothing against a unique partial index (`events_reflection_claim_idx`, `0006`) — and goes on only if its row came back, so a page open and a chat turn handing over the same session at once can't double its evidence (`reflectedOn` sees a claim or, for older sessions, `reflection.ran`; a run that dies after its claim leaves the session unreflected — at most once). What it reads is bounded to the session: the evidence already recorded, check-ins and transcript run from the start (the transcript from ten minutes before) to five minutes after the end, and evidence already recorded keeps its own op (`memory.contradicted` is a contradict, not a confirm). Sessions ended in a chat turn are handed over by the route; a session the sweep closed as *abandoned* was handed over by the Chat page and by the next chat turn (whichever came first); since 2026-09-14 it yields no operations, because leaving a session open is not evidence. The claim is checked first, in one query, and `reflectAfterSession` remembers per process the sessions it has seen through (run, already reflected or claimed), so a session handed over again is looked at once (code review B10, B19; while sessions are set aside nothing hands one over). Dev log: `[reflect] session=… ops=N`, only when a reflection ran.

**Retrieval** (2026-09-13, replaces "inject all active beliefs, ≤ 40"). The snapshot loads every active belief (≤ 200, `loadBeliefsOrNothing` — never throws; a failure is `memoryUnavailable` and the turn carries on). The chat route then picks **≤ 12 for the turn** with `selectBeliefs` (`core/ai/memory-select.ts`, pure): up to 5 `preference`s and 3 `strategy`s always (how to be with them, what has helped them start — strategies by net evidence); then any belief whose content words overlap what the turn is about — the message (weight 3), a running session's goal and first step or a *Start with Lumi* title (2), the last few messages (1), threshold 2, so one word from the message is enough and one from an earlier turn isn't; then the freshest projects and facts (≤ 3). A guess (not their word) below 0.5 with nothing confirming it for 60 days *fades*: left out of the block, still found by `recall_memory` and shown in Settings — relevance decay, not deletion, derived at read time. When anything is left out, the block says more is held and `recall_memory` searches it. Lexical on purpose (shared stemming with reflection, `core/words.ts`); pgvector embeddings when words stop being enough. Strategies render with their evidence ("helped 4/5") so Lumi can prefer proven approaches.

**Provenance and what isn't kept** (2026-09-13, `core/domain/memory-rules.ts`, pure, applied in `applyBeliefOps`). *Their word is checked, not claimed:* the route hands the tools the last 8 user messages (`ToolContext.userWords`); `user_said` needs `their_words` found there (whole words, in order, case and punctuation aside) and carrying what they meant — three content words of two letters or more, or at least half the content words of the short message it's in, so "forget that" counts but "the book" lifted from a long message doesn't (code review B4) — else the belief is held as `lumi_inferred`; `correct_belief` and `forget_belief` refuse without a match. Guesses start at ≤ 0.6 (`boundConfidence`). *Screens:* secrets and instruction-like text are never stored, whoever asks. These are not privacy screens: secrets would ride along to the model on every turn, and an instruction kept as a note would read as Lumi's rules. Personal details — health included — are kept like anything else (Chanté, 2026-09-13: privacy waits; a sensitive-details gate was built and removed the same day). *Duplicates:* a create whose content words match an active belief (Jaccard ≥ 0.75) confirms that one instead — or, when the new one is their word and the old one a guess, supersedes it; a similar one (≥ 2 shared words) is returned so Lumi can correct or revise it rather than keep two. *Forgetting* deletes the row and its supersession chain and leaves a `memory.deleted` tombstone of one-way content keys (`contentKey`) that refuses the same inference later. *Framing:* beliefs are quoted, one line each, under a line saying they are data, not instructions — the store never becomes a prompt.

**Adaptation without settings.** Tone, pace, and how much Lumi says are `preference` beliefs read by the persona each turn. There is no tone picker in V1; Lumi learns it, and the user can see and correct it in "What Lumi knows".

**Guardrails (EF check applies here too).** Learning is invisible and free: no thumbs, no tagging, no "was this helpful?", no memory setup. Beliefs never become stored judgements about the person's worth or capability — they describe what works, not who they are. Everything is visible and deletable.

### The Library: memory that consolidates (2026-09-13, `feat/lumi-library`)

Chanté's direction: recent conversation lives on in Lumi's memory and is periodically revised, and what's meaningful is recorded in its rightful place — the Library — so that when a subject comes up again (a book she's writing) Lumi has a quick summary and the parts of its archive that bear on the moment. Four layers, each feeding the next:

| Layer | Holds | Written by | Reaches a turn as |
|---|---|---|---|
| Working memory | the last 30–39 messages (the window's start moves in steps of ten, for the prompt cache) | the route | the transcript |
| Recent memory | `episodes`: one per visit (or the start of a long one) — a few sentences on what you talked about, and where it was left | consolidation | *Lately, between you*: ≤ 3 that ended before the oldest message in view, from the last 14 days |
| The Library | `threads` (a persistent subject: title, the words they use for it, a summary Lumi keeps rewriting) and `thread_notes` (idea · decision · question · progress · detail; their word or Lumi's reading; current or superseded) | consolidation, and Lumi on their word (`add_to_library`) | *The Library*: ≤ 2 threads the turn touches, opened (summary + ≤ 6 notes that bear on the message), and an index of ≤ 12 others |
| Beliefs | how to be with them, what helps them start | `remember`, reflection | *What you know about them* |

**Consolidation** (`core/ai/consolidate.ts`). Runs off the response (`after()`) at the end of every chat turn and on opening Home — `consolidateAfter(db, user, { passes })`: up to `passes` stretches that need a model call per run — one by default, for Home and a chat turn alike, so a backlog catches up a visit per trigger instead of several back to back — moving past any stretch with nothing to keep on the way (≤ 20, no model call, one dev-log line `moved past N messages with nothing to keep`), one run per user per process (code review B18: Home ran three passes, and three `[consolidate]` lines followed one turn). A visit stays its own stretch however short: an episode is a memory of each visit (the Recent memory row above, the persona's *The Library*), so short visits aren't merged. The conversation's `summary_through_message_id` is the watermark. The messages after it are read by comparing `(created_at, id)` with the watermark row inside Postgres: `created_at` keeps microseconds and a `Date` read back keeps milliseconds, so a comparison from JS read the watermark message again, and when it ended its sitting that one message was the whole stretch, claimed onto itself on every run (live 2026-09-13; `consolidate` also refuses a stretch that ends on its own watermark). `pickBatch` (pure) takes the first stretch after it that's ready: a sitting once it's over (a later message came after a 30-minute gap, or none has for 30 minutes), or the first part of a sitting of 24+ messages still going (all but its last 8), capped at 80 messages. A stretch with nothing in it (no user text, under 60 characters) just moves the watermark. Otherwise one model call — Lumi's model at low effort, structured output: `CONSOLIDATION_RULES` + the stretch, the threads held, and the current notes of the ones it likely touches — proposes an episode, threads and notes. `clampConsolidation` (pure) keeps: thread ids that exist (a "new" thread whose title or alias is already held becomes that thread, and its new words become aliases); a new thread only when it earns its place — named in 2+ of their messages in the stretch, or 3+ notes filed to it — and ≤ 2 per run; notes that resolve to a thread, pass the screens (`memory-rules.ts`), don't repeat a current note, ≤ 14 per run, `user_said` only when `their_words` is in the stretch (otherwise Lumi's reading), `supersedes` only a current note of that thread; a summary rewrite only for a thread the stretch touched; **shelving** (2026-09-13, `feat/library-sections`) only of a loose thread (never one already shelved), ≤ 4 per run, three levels at most (`whyNotShelve`), under a held or newly earned thread — or under one new thread the model proposes only to gather loose ones, which earns its place by gathering 2 (one per run). **Concurrency and failure** (code review A1–A3, 2026-09-13). Before the model call a run takes the stretch's **lease** — one conditional `UPDATE conversations SET consolidating_until = now + 3 min WHERE` the watermark is still where it found it and no lease is held or the held one has run out — so a second instance (or a Home open racing a chat turn) returns `busy` without paying for a model call; the lease is let go when the run ends, and one whose instance died runs out on its own. (A session advisory lock is unsafe through the transaction pooler, and a transaction held across a model call would pin a pool connection.) The plan then applies in **one transaction whose last statement claims the watermark** (compare-and-swap from where the run found it): the conversation row, which `saveMessage` touches on every turn, is locked only for the commit, and a lost claim throws inside the transaction so everything the run wrote rolls back (`lost`). A failed run — the model call threw, returned no structured output (never an empty stand-in, which would move the watermark with nothing kept), or the apply failed — leaves the watermark, appends `memory.consolidation_failed {from, through}`, and the stretch **backs off** by its recent failures from the same watermark: 10 minutes, then an hour, then six hours (`waiting`). The output schema carries no length or count limits (one over-long string failed the whole object); `clampConsolidation` truncates and caps. Event `memory.consolidated {messages, threads_created, notes, summaries, shelved}`; each move is its own `library.shelved`, and `shelveThread` refuses to move a thread the user placed. Dev log: `[consolidate] {…}`.

**Selection** (`core/ai/library-select.ts`, pure, lexical like belief selection). A thread *opens* when the turn touches it: its title or an alias said as whole words in the message (10), in Today's Right now (6; a running session or *Start with Lumi* until 2026-09-13), or in the last few turns (3); plus its title and alias words, weighted as for beliefs; plus half-weight overlap with its summary and notes, capped at 4. Threshold 5: a name in the message opens it, a passing mention a few turns back doesn't. Its notes rank by overlap with the turn, then newest. *Resting* (nothing for 30 days) is derived for the index, never stored. The Library block is headed as data, not instructions, and tells Lumi to pick up where a thread stands and never recite it. `loadLibraryOrNothing` never throws: a failure becomes a line saying the Library couldn't be read.

**Sections.** A thread can sit under a broader one (`threads.parent_id`). A top-level thread with threads under it is a section of the Library, a thread with threads under it inside a section is a shelf, the rest are books, and a top-level thread holding nothing is loose — all derived by `buildShelves` at read time. The Library block shows where an opened thread sits (`· in Coherence › Memory design`) and the index its section, so Lumi knows where things are without the user remembering (Library §39).

**Tools.** `open_thread` (now with `in`, where it sits, and `holds`, what's under it) and `search_library` read. `shelve_thread` moves a thread on their quoted words — under another (`under_id`), under a new section it makes (`new_section`), or off its shelf (neither) — as the user's placement, which Lumi won't undo (`shelveThread(…, "lumi", { theirWord })`: the event says `by: lumi, their_word: true`, the thread `shelved_by = user`). `add_to_library` files a note on their ask — a new thread only with their quoted words; `supersedes` when it changes a note. `forget_from_library` deletes a note (with its lineage) or a whole thread on their quoted words, leaving a `library.forgotten` tombstone of one-way keys so consolidation can't file it again from the transcript, which is never touched.

**What it is not, yet.** No embeddings: a thread opens on its words, so "chapter four" without the book's name stays closed unless the index or `search_library` finds it — meaning-based retrieval is the next layer. Sections are shown in the Library (`/library`, see features.md) but corrected only in conversation — no dragging yet; a thread has one place and no cross-links; the painted close-ups of the spatial map aren't generated, so a section opens on parchment over the wide room. Episodes don't compress further (weekly or monthly digests), threads don't merge or link to intentions, and consolidation doesn't propose beliefs.

### Lumi's design notebook — design partners only (2026-09-14, `feat/design-contributions`)

Chanté's ask: while she documents Coherence's philosophy, function and environment, Lumi notices meaningful ideas, tensions and implications in their design conversations and contributes them **without asking for approval each time** — she would rather discard what doesn't fit than carry the noticing herself — and a daily digest brings them to design and implementation work. Not authority to rewrite the philosophy, edit the canon or implement anything.

**Who.** `COHERENCE_DESIGN_PARTNERS` (comma-separated `users.id` or Clerk user ids; optional, `.env.example`) names the people designing Coherence, and `isDesignPartner(user)` gates everything: only their turns get the persona's *Designing Coherence with them* section (`DESIGN_PARTNER`, appended after the persona by `personaFor`), the two tools, the context section and the digest. Everyone else's cached prefix is byte-identical to before; `prefix.test.ts` pins both. Within a partner's conversations the persona scopes capture to talk about designing Coherence: their own tasks, days and life are never design evidence.

**Store** (`design_contributions`, `design_contribution_revisions`, `design_digests`, migration `0008`; `core/domain/design-contributions.ts`; kept apart from `docs/` and the canon). A note has a stable number (DC-12), a kind (insight · tension · assumption · possibility · shift), a free-text area, a title and **layers kept apart**: the *stated direction* (`stated_source: their_words` only when the quote is found in their recent messages by `findTheirWords`, else `lumi_paraphrase`), Lumi's *insight* (always her reading), a *possibility* (a design idea, never implied by the insight), why it might matter, what's unresolved, what prompted it and the source message id, related notes and supersession links both ways. Each part has its own **explicit** status — `insight_status`, `possibility_status` — `unreviewed` until the user says something about that part, then `endorsed · qualified · corrected · rejected`. Every change appends a revision holding the whole note after it (actor `lumi` or `user`; for feedback the part, the verdict and their words), so nothing is overwritten silently, and a revision's monotonic id is the digest's watermark. Screened like memory (`screenMemory`: no secrets, nothing that reads as an instruction to Lumi). A near-duplicate of any held note — withdrawn and rejected ones included, so a turned-down idea doesn't come back under a new number — isn't kept; the tool returns `already_held` with its id.

**Writing.** `contribute_design` keeps a new note at once (no approval step); with `revises` it revises or (`retract`) withdraws one of hers; with `supersedes` a new note replaces an older one (both kept); `related` links notes. When Lumi rewords a part, that part goes back to `unreviewed`: the endorsement was of the old words. `design_feedback` records the user's explicit reaction to one part of one note, on their checked words (no match, no feedback); it moves only that part's status — endorsing the problem never endorses the proposed interface, and related notes are untouched — and a qualify or correct may carry the part's new wording, the old kept in the history. The same reaction sent again (same part, verdict and words as the note's last revision) is kept once: the first real-model run sent one rejection twice in a reply. Nothing else moves a status: not silence, not a digest, not time. No code path writes a canonical doc, the repository, an intention, a belief or the Library from a note. Events `design.contributed`, `design.revised`, `design.retracted`, `design.feedback`, `design.digested`; ledger lines *Design note · DC-3 · title* (and *revised*, *withdrawn*), *Design feedback · DC-3 · possibility rejected*.

**Retrieval** (`core/ai/design-select.ts`, pure, lexical like beliefs). The context block's *Your design notebook* carries ≤ 6 current notes — up to 3 changed in the last 36 hours (continuity inside a design conversation), then those the turn is about — each with its statuses and whose words, and the user's last ≤ 5 feedback items (on notes in view first), framed as each about that one note, not a rule. Headed as reference, not instructions, and never a requirement. `loadDesignNotebookOrNothing` never throws.

**The digest** (`core/domain/design-digest.ts`, no model call). `generateDesignDigest(db, user, now)` takes the revisions after the previous digest's `through_revision_id` — contiguous, up to the end of the user's previous local day, and at least 2 minutes old (`DIGEST_SETTLE_MS`, so a write still committing below a newer id isn't skipped) — and builds markdown from each touched note as it stood at its last revision in the window: *Changed, corrected or withdrawn* (rejections, corrections, withdrawals, supersessions, and revisions of notes an earlier digest showed) · *Your stated direction* · *Endorsed by you* (endorsed is not a requirement, and covers only that part) · *Unreviewed — Lumi's hypotheses and possibilities* · *Open questions*; grouped by area, related notes adjacent, each with its DC number and source message. Unchanged notes aren't repeated. Nothing settled: no row (`nothing`). A window whose notes were made and withdrawn before any digest showed them: a row with null markdown that only moves the watermark (`quiet`), never filler. **Retry-safe:** `from_revision_id` is unique per user, so a retry or a racing run over the same window inserts nothing and returns the digest already made (`already_made`); a failure before the insert changes nothing; each digest starts at the last one's `through`, so no change falls between. **When:** off the response (`after()`) on a design partner's chat turn once their local day has turned since the last digest (`designDigestAfter`, one run per user per process, never throws) — no cron, like reflection and consolidation; notes only come from chat, so a day with no turn has nothing new. **Scheduling it anyway** (a digest ready before the day's first chat): run `npm run design:digest -- --generate` daily (a Claude Code scheduled task, or cron on a machine with `.env.local`), or add a Vercel cron calling a `CRON_SECRET`-gated route that runs `generateDesignDigest` for `designPartnerUsers` (the route audit accepts `CRON_SECRET`; `/api/cron/*` would need adding to `lib/public-paths.ts` for the proxy). Repeats are harmless.

**Consuming it.** Design and implementation sessions: `npm run design:digest` (the latest digest) · `-- --all` (the last seven) · `-- --notebook` (every note with its history) · `-- --generate` to make the next one first. In a browser, signed in as a design partner: `/api/design-notes` and `/api/design-notes?view=notebook` (plain text). No page, badge, count or review queue in the app; feedback happens only in conversation.

**What it is not, yet.** No embeddings (notes are chosen by their words); areas are free text; the digest isn't sent anywhere; keeping capture to design talk is the persona's instruction, not a classifier, so a stray note is corrected by saying so (`design_feedback` reject, or Lumi withdraws it).

### Conversation window
One continuous `main` conversation per user (Lumi is a person you keep talking to, not a folder of chats). The route loads the last 39 messages and the conversation's count, and keeps 30 to 39 of them: the window starts at a multiple of ten counted from the first message, so it holds still for about five turns and the history's prefix caches (The prompt, above). Pages still show the last 30. Older conversation reaches a turn as recent memory — episodes, above — rather than a rolling summary: `conversations.summary` is unused, and `summary_through_message_id` is consolidation's watermark (2026-09-13). Time gaps between messages are rendered in the UI as fine rules with a date, and passed to the model as the visit-gap line — not as fake messages.

### Privacy posture
- Model calls happen only on the server; the key never reaches the client.
- Every table is keyed by `user_id`; export and delete are a single cascade.
- Conversation text never goes to Vercel logs; log ids and durations only.
- Mail: read-only, and read only when Insights is opened (at most once per 30 minutes) or when the user asks Lumi to look. Message text goes to the model for that one call and is **never stored** — a lead keeps sender, subject, received-at and Lumi's own line. Tokens stay in Clerk. Disconnecting is Clerk's account panel → Connected accounts.
- Shared files (2026-09-13): a photo, PDF or text file shared from Home's composer travels inline in the chat request (a data URL on an AI SDK file part), goes to the model for that one turn, and is **never stored** — `noteSharedFiles` (`core/shared-files.ts`) puts a `data-shared-file` part (name and kind) in its place before the message is saved, so neither the database nor any later turn's history holds the file. No upload endpoint, no storage bucket. Text files reach the model as text (`readSharedFiles`): OpenAI's Responses API takes only images and PDFs as files.
- Lumi's requests go to OpenAI with `store: false`; OpenAI's API may still keep them up to 30 days for abuse monitoring (check the current terms), so note this in the eventual privacy page. Zero-data-retention is an org-level option to revisit if Lumi gets real users. (Under `LUMI_MODEL=anthropic:…`, Anthropic's standard retention is 30 days.)

## 3. Decisions that are expensive to reverse

| # | Decision | Pick | Why it's sticky |
|---|---|---|---|
| 1 | **Message storage shape** | Store AI SDK `UIMessage` parts as JSON, one row per message, with `format_version` | Chat history migrations are miserable; every renderer and the model-message conversion depend on it. Version it from day one. |
| 2 | **Append-only `events` table from day one** | Yes, every state change writes one | You cannot backfill behaviour you didn't record. Pattern memory, "what helps you start", and any future analytics depend on it. Costs one insert per write. |
| 3 | **Internal user ids vs auth-provider ids** | Internal UUID; `clerk_user_id` is a unique column | Swapping auth providers otherwise rewrites every foreign key. |
| 4 | **One thread per user vs chat sessions** | One `main` conversation + summary | Shapes the UI, context assembly and memory. Going from sessions → one thread later means merging; the reverse is easy (add `kind`). |
| 5 | **Framework-free core** | `src/core` has no Next/React imports; enforced by an ESLint `no-restricted-imports` rule | Mobile/CLI/cron reuse depends on this boundary existing before code accretes around Next. |
| 6 | **Timezone per user, stored** | `users.timezone` (IANA), captured on first visit. **Every day the model or the user is shown is a local day** — `localDate(at, timezone)` (`core/time.ts`), never `toISOString().slice(0, 10)` on an instant. (`Date.UTC`-built dates are already local calendar fields, so date arithmetic in `due-date.ts` and `priorities.ts` reads them back with `toISOString` on purpose.) | "Today", "yesterday", visit gaps, capacity-by-day all depend on it; retrofitting is a data-quality problem. West of UTC, an evening instant formatted as UTC is tomorrow — and the whole product is framed in days. |
| 7 | **Soft status, not hard delete, for intentions** | `open | done | dropped`; no delete | A dropped intention is signal (what gets abandoned). Deleting loses it. |
| 8 | **Tools as the only write path from the model** | Yes; no free-text parsing, ever | The moment prose parsing exists, structure erodes and the UI can't be trusted. |
| 9 | **Deterministic greeting** (and check-ins, until they went with sessions on 2026-09-13) | Not model-generated | Cost, latency and predictability; also keeps Lumi quiet by construction. Reversible in code, but the product feel depends on it. |
| 10 | **Model provider abstraction** | AI SDK provider + one `model.ts` module | Lets you move to Bedrock/Vertex/local for privacy without touching the app. Cheap now. |
| 11 | **Structured client events as user messages** | `session_event`/quick-start messages are real user messages with a metadata part | Keeps one transcript, one persistence path, one cache prefix. A side channel would fork the context. |
| 12 | **Beliefs carry confidence, evidence and supersession history** | Schema from day one | Confidence and evidence are what make learning possible; adding them later means every existing note is unweighted. Supersession keeps a correction from erasing history. |
| 13 | **Model proposes, code applies** | Reflection returns operations; `core/domain/memory.ts` applies them with guardrails | The alternative (the model writing beliefs freely) is unauditable and unsafe. The op format is a contract both sides depend on. |
| 14 | **Interventions link to outcomes via events** | `approach` on sessions; ids on completion events | Without the link, "what helps you start" is guesswork forever. |
| 15 | **Intentions stay flat in V1** | No projects table; `memory_notes.kind = 'project'` carries project context | Adding `parent_id` later is one nullable column. Adding a projects hierarchy first would drag the UI toward a task manager. |

## 5. API routes

Every exported method handler in a `src/app/**/route.{ts,tsx,js,mjs}` must call `requireUser()` or `requireVisit()` (or check `CRON_SECRET`) in its own body; `npm run check:routes` asserts it statically, per handler, with comments and strings ignored, and fails on any top-level `"use server"` file under `src/` (a server action is a public endpoint; this app uses routes). ## 6. Key conventions

- **`src/core` is framework-free** — no `next`/`react` imports (eslint-enforced). Domain logic and AI assembly live there; unit tests too.
- **Model reads via the context block, writes via tools.** Every tool write appends an `events` row. Never parse prose for state.
- **Deterministic where it can be:** the greeting, quick starts, and the fixed questions on Today (the capacity prompt, *Not this*). Lumi never speaks unprompted (check-ins, the one exception, went with sessions on 2026-09-13).
- **Store facts and events; derive judgements** (stale, avoided, gap, today's capacity). Never persist derived flags.
- **Fresh on every visit** (2026-09-13, Chanté: "make sure we reload when anything changes"). Pages are `force-dynamic` and read the database on every render; nothing a page shows is copied into a cookie, a token, the browser or a cache. Speed comes from fewer and parallel round trips (`requireVisit`, `Promise.all`), not from keeping old copies. The ways back that skip the server re-read: `components/shell/FreshOnReturn.tsx` calls `router.refresh()` after Back/Forward and on returning to a tab left a minute or more; a write from a page's own control refreshes it (`router.refresh()` in `CompleteCircle`, `RightNowActions`, `CapacityPrompt`, `LeadActions`), and a turn in the companion bubble refreshes the page under it. **Anything that changes when something else is updated** (the Library's section signs, when they come; a count, a badge) is read at render like everything else. If something is ever cached for speed (`staleTimes`, `unstable_cache`, `"use cache"`), every write that changes it must invalidate it in the same change, and the entry in `features.md` must say which writes those are.
- **Beliefs:** model proposes ops, `core/domain/memory.ts` applies with guardrails. `user_said` beliefs are never retired without the user.
- **Cached prefix stays byte-stable:** persona + tool descriptions first, then the conversation, and the volatile context last (on the newest user message). `src/core/ai/prefix.test.ts` pins the sha256 of the persona plus every tool's description and input schema, for mail on and off: a change fails `npm run check` until the hash is updated on purpose. Verify with the `[chat] tokens` dev log line (`cacheRead` > 0 from the second turn, and close to the whole input once a sitting has a few turns). OpenAI caches a prefix of 1024 tokens or more on its own (the persona + tools clear it); Anthropic's minimum is model-dependent. A short persona may never cache, so grow it before assuming a bug.
- **Indexed access is checked** (`noUncheckedIndexedAccess` in `tsconfig.json`, code review E1, 2026-09-13): `arr[i]`, `record[key]` and a regex group are `T | undefined`, so the not-found case is handled where it happens: a guard that returns what the function already returns for nothing (`undefined`, `null`, a `Skip`), `.at(-1)` or destructuring (`const [first] = rows; if (!first) …`), or a clear throw. A write that must return its row goes through `returnedRow(rows, "<write>")` (`core/domain/rows.ts`), which throws naming the write. No `!` in app code except where the index is provably in range, with a comment; tests may use `!`. Look a word up in a `Record` with an own-property check (`Object.hasOwn`), never `in`: `"constructor" in {}` is true.
- **Message ids are UUIDs on both sides** (`generateId: () => crypto.randomUUID()` in `useChat`, `generateMessageId` in the route) because `messages.id` is a uuid column.
- **Proxy wall without `createRouteMatcher`** (deprecated in Clerk 7): `src/proxy.ts` matches the public prefixes by hand (`isPublicPath`, `src/lib/public-paths.ts`, the same list that keeps the nav off the sign-in and sign-up pages) and calls `auth.protect()` for everything else; every page and route still calls `requireUser()` or `requireVisit()` itself (Clerk's resource-based recommendation; the route-auth audit accepts either). With the local test user on (`COHERENCE_DEV_USER=1` under `npm run dev`, Env above) the proxy returns before `auth.protect()` and both helpers answer with the test user's row instead of reading Clerk's session.
- **Clerk only in `src/lib/auth.ts`, `src/lib/auth-ui.tsx`, `src/lib/auth-mail.tsx`, `src/proxy.ts` (the middleware) and the sign-in/sign-up pages.** Internal `users.id` everywhere else. The Google token for mail is fetched in `auth.ts` and handed on as an `EmailReader` (`lib/email.ts`), so `src/core` never sees Clerk or a token.
- **Copy lives in `src/core`** (greeting, persona, canned quick-start messages), not in components — so the voice is reviewable in one place.
- **No counts of undone things anywhere in the UI.** If a number would make someone feel behind, it doesn't ship.
- **EF-burden log** (`docs/ef-burden-log.md`) gets a row for every new user-maintained state, in the same commit.

## 7. The day plan (M3)
`core/ai/plan.ts → buildDayPlan()` asks the model for `{ dayLine, rightNow, afterThat, closingLine }` via structured output (`Output.object`) with the persona + planner rules + a compact inputs block (candidates with flags, fixed-time items, capacity, declined reasons, how-they-work beliefs). `clampPlan()` (pure, tested) enforces: ids must exist, no repeats, ≤3 after-that (≤1 on a low day), fixed-time items only in `later`, counts stripped from lines. Persisted per local date (`day_plans`). `core/ai/today-plan.ts → ensureTodaysPlan()` is the one reader/generator: it returns the persisted plan, or generates and saves it once per user per day (an in-flight map dedupes concurrent callers in a process; re-cuts, and a first generation, run one at a time per user — `serially`, `core/ai/serial.ts` — each on the snapshot the one before saved, so a capacity answer racing a `reshape_today`, or two quick reshapes, leave the path of the last request; a generation that waited behind a re-cut keeps the re-cut's path. Per process only; code review B8). It is **primed off the response** — `primeTodaysPlan()` in Next's `after()` on the home page and at the end of a chat turn that could have changed it (`needsPrime`, API routes above) — so the model call (several seconds) has usually already happened by the time Today is opened; Today reads the snapshot once per request (`react.cache`, shared by `planIsReady` and the three `PlanSection` parts): when the path is already cut the page renders whole with no Suspense (a placeholder swap costs at least React's 300ms reveal throttle, which read as the card arriving late), and only when it still has to be generated do the parts stream in under Suspense and pay for the model. One code-derived refresh: a plan cut with nothing to choose from is re-cut (`reason: first_items`) once intentions exist, since priming on open makes "open app → brain-dump → Today" the normal order. A plan with a Right now is never regenerated by this path. Closing an intention anywhere advances the path in code (`plan-sync.ts`).

**Re-cuts (M4).** `recutTodaysPlan(db, user, reason | { reason, ask? })` is the only way an existing Right now moves, and it runs on exactly four triggers: `capacity` (Today's prompt via `/api/capacity`, or the `report_capacity` tool — skipped when the answer matches what the plan already assumed, e.g. normal-ish on a plan cut without a report), `declined` (a *Not this* answer arriving in `/api/chat`), `reentry` (`drop_intention` during a sitting that began after ≥ 7 days away), and `asked` (the `reshape_today` tool: the user asked in chat for a different shape — "something easy", "what should I do now"; `PlanInputs.ask` carries the words and Lumi's pick, the planner rules say the ask outranks the default order, and `clampPlan(…, pin)` forces the pick into Right now — over the model and over a decline earlier today — so Today matches the reply). Chat-side triggers are collected during the turn (`ToolContext.onPlanChange`, the declined metadata) and applied once in the route's `after()` — `primeTodaysPlan(db, user, recut)` — so nothing waits on the model twice. The planner sees today's declines with their reasons (`snapshot.declinedToday`) and `clampPlan` refuses to put a declined intention back in Right now, even if the model proposes it; it may still sit in After that ("too tired" is about now, not never). When everything left has been declined today, Right now is empty with a fixed line rather than a re-proposal. The gap passed to the planner is the one the *sitting* began after (`visitBeforeSitting`), not the seconds since the last request.

## 8. Data access

- `src/db/schema.ts` is the single source of truth for tables and their TS types (`User`, `Intention`, …). `docs/domain.md` is its prose twin — update both in the same commit.
- `db()` (`src/db/client.ts`) is a lazy singleton — kept on `globalThis`, so a dev HMR re-evaluation doesn't open another pool of 10 (code review A15) — over `postgres` with `prepare: false` (Supabase transaction pooler, port 6543) and a pool of 10 that keeps idle connections for thirty minutes (the pooler keeps them alive: 6 and 12 minutes idle answered in ~70ms with no reconnect) — opening one costs ~0.5s against ~70ms per warm query (Vancouver → us-east-2), so a pause between page views must not cold-start the pool. **The pool opens whole** when it is made (`warm`, all 10 at once): the driver opens a new connection for any query that finds none free rather than waiting for a busy one, so a cold page's parallel reads each paid to connect (Today's nine: ~510ms, warmed ~90ms). It warms on every cold instance, even one whose first request needs one query — kept on purpose (A15, `decisions.md`). **`max_pipeline: 0` is load-bearing:** by default the driver pipelines a query onto a busy connection once all are busy, and through the transaction pooler that query is never answered (a warm pool of 5 hung on its 6th parallel query; the snapshot sends 7). With 0, extra queries wait for a free connection. **It also breaks the driver's own transactions**, so `connect` replaces the pool's `begin`: the driver's `sql.begin` (what drizzle's `db.transaction` calls) reserves its connection in an `onexecute` callback that `execute()` only reaches while `sent.length < max_pipeline` — never, at 0 — so BEGIN ran on an unreserved connection and the driver refused it (`UNSAFE_TRANSACTION: Only use sql.begin, sql.reserved or max: 1`); consolidation failed on every run until 2026-09-13. `beginOnReserved` runs BEGIN, the work and COMMIT or ROLLBACK on `sql.reserve()` (one held connection, which is what the transaction pooler expects of a transaction), with savepoints for a nested `tx.transaction`, so `db.transaction` is safe anywhere. `client.db.test.ts` runs the pool with production's options over a real Postgres wire and pins the driver's refusal, so a driver upgrade that changes either shows up in `npm run check`. The functions run in `cle1` (Cleveland, `vercel.json`), next to the database in us-east-2. Import only from server code.
- Domain functions in `src/core/domain/*` take the `Db` as their first argument (no module-level client) so they're testable against a scratch database and liftable into a worker.
- Every write goes through a domain function that also calls `appendEvent` — never `db().insert(...)` from a route or component.
- **A write of more than one statement is atomic** (code review A9, 2026-09-13): `atomic(db, tx => …)` (`core/domain/tx.ts`) opens a transaction, or joins the one `db` already is — consolidation filing notes, a lead kept as an intention — without a savepoint per step. Everything inside takes `tx`, never the outer `db` (on PGlite a query on the outer handle waits for the transaction and never returns). Belief ops read the belief they change `FOR UPDATE` and move counters in SQL (`evidence_for + 1`), so two confirmations at once count twice. Supersession chains are walked in one recursive query (`core/domain/chains.ts → chainIds`) for forgetting a belief or a note. Where two concurrent writers must not both succeed, a unique index says so (one main conversation, one open session, one lead per message and title, one reflection claim per session) and the insert is `on conflict do nothing`.
- `ensureUser()` and `visit()` (`core/domain/users.ts`) are the only places a Clerk id enters the data layer; `src/lib/auth.ts` wraps Clerk's `auth()` (local session-cookie check) around them and returns the internal `User` row; the Clerk profile (`currentUser()`, a network call) is fetched only when the row has to be created, so it never sits on the request path. Timezone arrives via the `coherence_tz` cookie (`components/shell/TimezoneCapture.tsx`) and is kept current on every request. **A page open or a chat turn calls `requireVisit()`** (Home, Today, Lists opened directly, the Library, Insights, `/api/chat`): one `UPDATE users … FROM users AS before … RETURNING` finds the row, stamps `last_seen_at` and the timezone, and returns the row as it was before (so `lastSeenAt` is the previous visit) — one round trip where `requireUser` + `recordVisit` were two; `app.opened {gap_seconds}` is written when the gap was ≥ 30 min, so `last_seen_at` is always the last request and the newest `app.opened` is always the start of the current sitting. Only the first request ever creates the row first (`requireUser` + `touchLastSeen`). Routes that don't count as a visit (capacity, session, intentions, leads), Settings, and the Lists sheet opened from the nav (the page underneath already counted) call `requireUser()`.
- **The sitting, not the last request, carries the gap.** `loadSnapshot` includes `currentSitting` (newest `app.opened`). The greeting on Chat, the context block and the planner all read the gap the sitting began after, so "came back after two weeks" survives navigating Today → Chat and the fifth turn of the visit, and disappears once they've said something this sitting (greeting) or the next sitting begins (context). The route's `lastSeenAt` (previous request) still drives "same sitting" / "last here: 3 hours ago".

## 9. Mail and leads (2026-09-12)

**Switched off 2026-09-13** (`MAIL_ON = false`, `core/email/types.ts`), so Google sign-in asks for nothing restricted and the consent screen can be published without Google's review (`pre-prod.md`). The switch is a constant, fixed per deploy, so the cached prefix stays byte-stable. Off: `buildTools` leaves out `look_at_email`, `keep_lead` and `dismiss_lead` (`mailTools`), the persona leaves out its mail line and *Their mail* in the id list, the chat route skips the leads and last-look queries, passes no reader and no `mailScan` (so the context has no *Their mail*), the nav leaves out Insights and `/insights` redirects Home. `leads` rows and `email.scanned` events are untouched; `/api/leads/[id]` still answers but nothing calls it. Past messages with mail tool parts still render their ledger lines (`ledger.ts`). Turning it back on is the constant plus `gmail.readonly` back on the consent screen. What follows describes it with mail on.

Lumi can look through the user's recent mail, notice what might need doing, and ask — once, on the Insights page — *do any of these still need doing?* The pattern is the day plan's: **model proposes, code guards, the user answers with one tap.** Nothing is synced, cached or counted.

- **Access.** `lib/email.ts → mailAccessFor(user)` asks Clerk for the Google OAuth token (`auth.ts → googleAccessToken`) and returns an `EmailReader` (`core/email/gmail.ts`), or `not_connected` / `needs_scope`. The Insights page places `ConnectMail` (`lib/auth-mail.tsx`): `user.createExternalAccount({strategy: "oauth_google", additionalScopes: [gmail.readonly]})`, or `reauthorize` on an existing Google account, then follows Clerk's redirect; Google sends the browser back to `/insights`.
- **One look** (`core/email/scan.ts → ensureFreshMailScan`). Runs when Insights is opened and the newest `email.scanned` is older than 30 minutes; in-flight per user per process, and across instances the unique `(user_id, source_ref, lower(title))` index keeps a lead from landing twice. Reads the inbox (minus promotions and social) newest first since the last watermark (first look: 7 days), a page of 30 at a time, paging back with `before:` for up to 2 pages (≤ 60 messages to one model call). What a look runs out of pages for is recorded as `backlog` and read by the next look after what's new (code review A12, 2026-09-13: the watermark used to move to the newest message, so anything past the newest 30 was never read); a backlog older than a week is dropped. It skips message ids that already produced a lead, and makes **one model call** (`core/ai/leads.ts → inferLeads`, persona + reading rules + the messages, plus the open intentions and recently kept/let-go titles so nothing is suggested twice). `clampLeads` (pure, tested): message ids must exist, ≤ 2 per message, confidence ≥ 0.5, ≤ 8 total, no repeats, no known titles, list only if it is one of theirs, due only if it parses (`dueAtFromModel`: a bare day is 00:00 that day in their timezone, as for `create_intention`), counts stripped. Leads are inserted (`lead.suggested`), the look is recorded (`email.scanned {through, read, suggested}`), and a Gmail 401/403 surfaces as *disconnected* with the connect chip, never an error page.
- **The answer.** Insights shows each lead as a card — title, why, sender · subject · when — with *Still needs doing* (→ `createIntention` with the lead's title, why + subject as the note, list, due; `lead.kept`) and *Let it go* (`lead.dismissed`; "done", "not a thing" and "not mine" are deliberately not distinguished). A lead is gone once answered. In chat the same leads sit in the context block under *Their mail*, and `keep_lead` / `dismiss_lead` are the same domain calls with `via: "chat"`.
- **Looking on request.** `look_at_email` reads fresh (a search, days back) when the user asks about their mail; the persona says never unasked, and never read the inbox back — answer in a few lines.
- **What is never built:** a mail list in the app, unread or "needs reply" counts, a sync job, a stored copy of any message.
