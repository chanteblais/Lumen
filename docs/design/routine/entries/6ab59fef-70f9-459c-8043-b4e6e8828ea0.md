### CURRENT CANON

Coherence already has the right philosophical stance toward memory: **Lumi carries organizational burden, but the user retains authority.** Explicit instructions outrank guesses, and manual correction is meant to be possible without turning organization into a maintenance ritual. fileciteturn14file0L9-L9 The canon also explicitly distinguishes information the user stated from information Coherence observed, inferred, or derived; those categories are not supposed to collapse into one undifferentiated “memory.” fileciteturn15file2L27-L27

Implementation is only partway there. Lumi already receives stored intentions, beliefs, recent activity, capacity, session information and other context, but the richer shared-life model is not yet fully first-class. fileciteturn16file1L18-L18

### OPEN QUESTION

Q12 asks how users should **inspect and correct what Lumi knows** without creating memory-curation work. Whether that needs a dedicated surface—and how it relates to Library and conversation—is deliberately unsettled. fileciteturn12file0L9-L9

I think the tempting solution is also probably the wrong primary solution: a big **“What Lumi knows about you”** page full of editable facts.

That would technically provide transparency, but it would give the user another database to audit.

### PROPOSAL — **Memory receipts, not memory management**

Make memory inspectable **at the moment it has consequence**.

Whenever remembered context materially affects what Lumi recommends, changes, or concludes, Coherence can leave a tiny provenance affordance alongside the result. Not on every sentence, and not for trivial contextual continuity—only when the remembered information actually changed the system’s judgment.

For example, Lumi might recommend practicum work first and quietly append:

*Based on something you told me →*

Opening that would reveal a small “receipt”:

**Practicum comes first this month**  
*You told me this · September 8*

Then perhaps three restrained actions:

**Still true** · **Update** · **That was temporary**

An inference would look different:

**Mornings may be harder for focused work lately**  
*Something I’ve noticed — not something you told me directly*

The language matters. I would avoid exposing confidence scores like `0.73`; humans do not need to administer the model. The provenance itself—*you told me / I noticed / I inferred this / derived from X*—is much more legible.

Corrections should also be **semantic rather than destructive by default**. If the user says *“That was only true while I was sick,”* Coherence does not need to pretend the earlier information never existed. It can learn its scope and supersede it:

**Mornings were difficult while sick → no longer assumed generally.**

That connects neatly to the earlier priority proposal too. If Lumi invokes *“Practicum comes first this month,”* the user can inspect the exact declaration that influenced the recommendation rather than wondering what invisible ranking system produced it.

I’d make one rule especially firm:

**The more consequential the use of memory, the easier its provenance should be to inspect.**

Casual conversational continuity can stay invisible. Choosing one task over another might warrant an optional receipt. Reinterpreting a long-term priority, acting on an inferred preference, or making a meaningful recommendation should make its basis readily inspectable.

This also gives Q19—consequential inference visibility—a natural answer without requiring every inferred belief to become a permanent visible object. The distinction already exists conceptually; the receipt exposes it exactly when it matters. fileciteturn15file0L9-L9

I would still leave room later for a sober global surface for things like retention, export, deletion, or broad inspection once those policies are settled. But **routine trust should not depend on periodically visiting Settings and cleaning Lumi’s brain**.

The principle I’d add to the design language is:

**Transparency follows consequence, not storage.**

That feels very Coherence to me. The user does not need to know everything the system knows at all times. They need to understand **why it mattered here**, and be able to correct it immediately when it is wrong.

I wouldn’t mock this one up yet. It should probably reuse the existing quiet ledger/conversational language rather than introduce a major new visual surface; the important decision is the interaction rule.
