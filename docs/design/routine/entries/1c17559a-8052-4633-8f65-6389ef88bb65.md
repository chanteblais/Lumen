## DIRECTION

I think the next concept that deserves first-class structure is **Thread**.

Not Action.

Not Relationship.

Not a full Intention/Action split yet.

Thread is the one structure that can make almost everything Coherence already does more coherent **without forcing the user to change how they use the app**.

A Thread is already defined conceptually as persistent context across fragmented activity, and that is exactly the thing the current system is weakest at representing.

Right now Coherence can know many related pieces:

> send the proposal  
> wait for feedback  
> remember what happened in the meeting  
> notice an email about the same issue  
> talk with Lumi about uncertainty  
> decide the project is no longer worth pursuing

Those may all belong to the same continuing thing in the user’s life, but an intention list does not really express that.

## OPEN QUESTION

This is **Q22 — Which concepts become structure first?**

The question specifically warns against prematurely building the entire ontology. That constraint is important.

The useful next step is not:

> Let’s formalize every kind of human context.

It is:

> **What single piece of structure would reduce fragmentation across the most existing behaviours?**

My proposal is that Thread is that piece.

## PROPOSAL — **Make Thread the first durable container of continuity**

A Thread should be a stable identity for **something that continues to matter across multiple moments**, regardless of whether it currently has a task attached.

Examples could be:

> Finding a practicum placement

> Moving house

> Figuring out whether to stay in this relationship

> Coherence itself

> My health this year

> Dad’s estate

Some resemble projects.

Some absolutely do not.

That distinction is important. I would avoid defining Thread as “project, but broader.” A Thread is primarily about **continuity of meaning**, not a deliverable.

### The first version should be extremely small

I would not launch Thread with milestones, statuses, subprojects, owners, due dates, kanban views, or a hierarchy.

A first-class Thread really only needs a few things underneath:

**Identity** — a stable internal ID and a working name.

**Current orientation** — a short living summary of what is going on *now*.

**Relevant history** — references to meaningful past context that should remain retrievable.

**Connections** — existing intentions, conversations, calendar events, noticed external signals, or beliefs that relate to it.

**Provenance** — whether the Thread was explicitly established by the user or inferred by Lumi.

That is enough to change the system substantially.

The Thread itself does **not** need to own every object connected to it.

An intention can be connected to a Thread.

A conversation can be connected to several Threads.

A calendar event might relate to a Thread without becoming an Intention.

A relationship might later become first-class but meanwhile still appear inside Thread context.

This is closer to a contextual graph than a folder hierarchy.

### Most Thread maintenance should happen invisibly

This is where I think Coherence can diverge sharply from tools like Notion, Things, or project-management software.

The user should not routinely have to decide:

> Which Thread does this belong to?

If Lumi hears:

> “Richard got back to me about the chapter.”

and there is an existing Thread around that work, she can associate the new context automatically.

That is administration.

It does not take agency away from the user.

If Lumi gets the connection wrong, the user can correct it conversationally:

> “That’s actually unrelated to the textbook chapter.”

and the relationship is removed.

No filing workflow required.

### Thread creation itself should have a slightly higher threshold

I would distinguish **associating context with an existing Thread** from **declaring that a new Thread exists**.

Association is usually low-consequence and reversible.

Creating durable structure about the user’s life is somewhat more interpretive.

So Lumi can internally notice a candidate pattern:

> several conversations  
> two intentions  
> a calendar event  
> repeated references to the same concern

But she does not need to immediately announce:

> New Thread created: CAREER TRANSITION

If the pattern becomes consequential, the interpretation can surface naturally:

> “This job-change question keeps showing up in a few different places. I’m starting to treat it as one ongoing thread. That seem right?”

A simple yes is enough.

An explicit user statement can bypass that entirely:

> “All of this is really part of figuring out whether I want to leave my job.”

That is already strong enough to establish the Thread.

This keeps the proposal compatible with the unresolved inference questions rather than pretending they are solved.

## The most useful thing a Thread holds is **current orientation**

I would not make the core of Thread a task list.

Its most valuable field may be a very short living summary like:

> **Current orientation**  
> Waiting for the revised contract. You’re interested, but compensation is still the sticking point. No decision needed until Friday.

That is dramatically more useful to Lumi than replaying twenty messages or treating every past fact equally.

It also means re-entry becomes much easier.

After three weeks away, Lumi does not need to say:

> “You have six incomplete intentions related to this.”

She can say:

> “Last time, you were waiting on the revised contract. It arrived while you were away, and nothing suggests you’ve responded yet. Want to pick that back up?”

That is continuity.

### A Thread can persist when there is nothing to do

This is probably the biggest reason I would choose Thread before splitting Intention and Action.

Someone might have a Thread:

> Mom’s health

with no current task.

Or:

> Whether I want children

with no task at all.

Or:

> Painting again

which has drifted into the background but still matters.

A task-centric model has trouble representing these without manufacturing obligations.

Thread can hold them honestly.

That makes it the structure most aligned with the broader shift away from “everything meaningful becomes action.”

## Threads also give earlier proposals somewhere coherent to land

This proposal would connect several of the previous explorations without resolving them prematurely.

A **scoped priority claim** can refer to a Thread:

> “Practicum is my main priority this semester.”

The **Noticed** system can associate an external signal with a Thread before deciding whether it becomes an obligation:

> “This email seems related to the practicum Thread.”

An environmental **trace of continuity** could eventually draw on a Thread’s sustained presence without rewarding task completion.

A Today recommendation can explain:

> “This is part of the thing you said matters most this term.”

And context selection can later retrieve the relevant Thread rather than stuffing every related memory into Lumi’s prompt.

This is why Thread has such leverage: it does not require those systems, but it gives them a shared semantic anchor.

## Library should eventually reveal Threads — but Thread should not wait for Library

I would explicitly separate the data-model decision from Q3’s still-open spatial design.

Making Threads first-class does **not** mean we should immediately put:

> THREADS

on one of the Library plaques.

That would jump ahead of the unresolved interaction design.

Threads can first improve:

- Lumi’s context,
- re-entry,
- Today reasoning,
- external-signal interpretation,
- memory reconciliation,

while remaining mostly invisible.

Later, Library can expose them in whatever browsing language actually fits the room.

That keeps the implementation order sane:

**make continuity real first → then decide how the room lets you encounter it.**

Not the reverse.

## What happens when a Thread ends?

I would avoid forcing an **Active / Completed** model.

Some Threads complete.

Some resolve.

Some are abandoned.

Some become irrelevant.

Some simply recede.

Some transform into something else.

So the underlying lifecycle should probably distinguish at least:

**Current** — actively relevant.

**Background** — still meaningful, not foregrounded.

**Closed** — no longer evolving, but preserved as history.

I would not make those statuses visible controls by default.

They are primarily context-selection tools.

If the user says:

> “That chapter is done now.”

Lumi can close that Thread naturally.

If they say:

> “I’m not thinking about the move until spring.”

that is closer to background/resting than closure.

If a Thread has simply gone quiet, **inactivity alone should not decide**.

That keeps the lifecycle aligned with the existing canon.

## Thread summaries should preserve change, not overwrite history

Suppose the Thread once said:

> You’re planning to leave your job.

Six months later:

> You decided to stay after your role changed.

The second should become current orientation.

The first should not vanish from history.

This is the same supersession principle already appearing elsewhere in Coherence:

**current truth changes; history remains historically true.**

That means Lumi can later understand:

> “You were seriously considering leaving before the promotion.”

without behaving as though leaving is still the plan.

## Why not Action first?

Eventually I do think Intention and Action should separate.

But doing that first mainly improves **task semantics**.

Thread improves the entire shared-context system.

The user can already create something resembling a concrete action through the existing intention schema. It is imperfect, but functional.

What the current system cannot represent nearly as well is:

> *all these fragmented things belong to the same continuing part of my life.*

That feels like the higher-leverage missing structure.

## Why not Relationship first?

Relationships matter enormously, but making them first-class first creates questions about person identity, contact resolution, roles, changing relationships, privacy, and cross-thread relevance.

Thread can already preserve relationship context in the meantime without pretending that the person ontology is solved.

Likewise, Commitments probably deserve first-class treatment eventually, but the existing due/fixed-time structures cover enough of the immediate behaviour that they are not the biggest conceptual gap.

So my proposed sequence would be:

> **Thread first.**  
> Let the current Intention object continue temporarily carrying intention/action behaviour.  
> Introduce richer structures only where Thread exposes concrete limitations.

Not because Thread is philosophically “more fundamental,” but because it gives the most coherence per unit of new system complexity.

## HISTORICAL / REJECTED

I would specifically reject turning Thread into:

- a mandatory project folder;
- another list the user has to curate;
- a hierarchy where every Intention needs exactly one parent;
- a taxonomy the user must define before Lumi can understand them;
- an excuse to build the entire life ontology at once;
- a dashboard of every Thread in the person’s life.

That would convert the shared model into another organization job.

The canon-level principle I would propose is:

> **Thread is the first-class unit of continuity. It connects fragmented context without requiring everything meaningful to become a task, and it should be maintained primarily by Coherence rather than by the user.**

I’m not generating a mockup for this exploration. The important decision is **structural rather than visual**, and Library’s concrete navigation is deliberately still open. Designing a Threads shelf, plaque, or browser now would prematurely resolve Q3 before the underlying concept has earned its interface.
