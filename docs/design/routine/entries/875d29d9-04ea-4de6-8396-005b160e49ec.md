The settled philosophy already puts strong limits around this. Lumi should be present without becoming an engagement machine: she speaks when useful, not because enough time has elapsed; leaving the app can itself be success; re-entry should not arrive with debt or failure. At the same time, Coherence is supposed to remember enough that the user does not have to keep noticing, tracking, and reconstructing everything themselves.

The current implementation contains a few kinds of initiative—return greetings, deterministic Focus Together check-ins, mail-lead discovery, and occasional re-entry support—but there is no general proactive system, notification policy, or settled rule for unsolicited intervention.

### DIRECTION

Lumi should sometimes be able to say **“this matters now”** without waiting for the user to remember to ask.

But proactive help should reduce vigilance, not create a new form of vigilance where the user starts wondering what Lumi will interrupt them about.

### OPEN QUESTION

**Q9 — What may Lumi initiate?**

I think the key mistake would be to define proactivity by topic:

- deadlines may trigger,
- priorities may trigger,
- email may trigger,
- inactivity may trigger.

Those rules become brittle quickly because the same information can be either valuable or intrusive depending on what changed, how certain Lumi is, and what the user is currently doing.

I’d instead define **when Lumi earns the right to interrupt**.

### PROPOSAL — **Proactivity requires a changed situation, not merely an important fact**

My proposed rule would be:

> **Lumi may initiate when something materially changed since the user last had a fair chance to account for it.**

That gives Coherence a surprisingly clean boundary.

Suppose the user already knows:

> “My practicum paperwork is due Friday.”

Friday approaching does not, by itself, justify Lumi repeatedly surfacing it. The user already incorporated that fact into their world.

But if the user learns through email that:

> the deadline has moved to Wednesday,

that is a **changed situation**.

Or if a calendar event appears that removes the only open block they had intended to use, the situation changed.

Or if the user explicitly told Lumi:

> “Remind me before I leave tomorrow,”

their instruction itself creates a future state in which intervention is authorized.

That leads to three main classes of legitimate initiative.

**1. Something changed outside the user’s attention.**  
A commitment moved, a relevant response arrived, a conflict appeared, or previously uncertain information became concrete.

**2. Something the user explicitly entrusted to Lumi became timely.**  
“Remind me,” “don’t let me forget,” “tell me if this changes,” or another scoped instruction. Explicit delegation should be the strongest form of permission.

**3. The user has crossed a meaningful transition where previously known context becomes newly relevant.**  
Opening Coherence after an absence, returning from Study, arriving at Today in the morning, or entering the period just before a known fixed commitment can justify a restrained orientation cue.

What would *not* qualify:

> “You haven’t worked on this in three days.”

Nothing necessarily changed.

> “This is one of your highest-priority tasks.”

Still true, but not new.

> “You usually work around this time.”

A pattern is not an invitation.

> “You haven’t opened Coherence today.”

Completely irrelevant to the user’s life.

That distinction protects the product from a huge class of superficially “smart” nagging.

---

I’d also give proactivity an **escalation ladder**, because initiative does not always need to mean interruption.

Most newly relevant information should enter at the lowest useful level:

**Silent incorporation**  
Lumi updates context and does nothing visible.

**Next-arrival mention**  
When the user naturally returns, Lumi includes the change in orientation:

> “One thing changed since yesterday: Richard moved your meeting to Tuesday.”

**In-app interruption**  
Only when the user is already in Coherence and the change is time-sensitive enough that waiting for another natural transition would plausibly hurt them.

**External notification**  
Reserved for explicit delegation or unusually clear, consequential, time-sensitive changes.

That last threshold should be high.

If Coherence eventually connects to mail, calendar, messages, and other systems, it will know hundreds of things that *could* be relevant. The product should not equate broad awareness with broad licence to interrupt.

The goal is almost the opposite:

> **Lumi can watch more so the user has to watch less.**

For that promise to work, Lumi has to be exceptionally selective about crossing from **knowing** into **speaking**.

### A useful consequence: no generic “notification centre”

I would resist adding a conventional notification bell with a growing stack of things Lumi thought were worth mentioning.

That recreates an inbox.

If something is worth interrupting for, surface it appropriately. If it is merely worth retaining, keep it in the shared model or Library. If it is no longer timely, let it disappear from foreground attention.

There can still eventually be notification preferences in Settings, especially for external alerts, but the product should not require the user to periodically clear Lumi’s accumulated observations.

### Lumi should be able to explain an interruption

This also connects nicely to the earlier memory-receipt idea.

If Lumi initiates something unsolicited, the user should always be able to understand **why now**.

Not:

> “I thought this might be helpful.”

But something concrete:

> “I brought this up because the deadline changed this morning.”

> “You asked me yesterday to remind you before you left.”

> “Your 3 p.m. commitment now overlaps the time you had set aside for this.”

That makes proactivity corrigible. If Lumi gets the boundary wrong, the user can say:

> “I don’t need reminders about that.”

And that instruction should have durable authority within its scope.

### HISTORICAL / REJECTED BOUNDARY

I would explicitly avoid engagement-based triggers, generic inactivity nudges, streak-preservation messages, “we haven’t seen you lately” outreach, or proactive prompts whose real purpose is bringing the user back into the product.

I would also avoid making Lumi proactively surface every plausible unfinished obligation simply because the system can detect it. That would convert Coherence’s richer life model into a more sophisticated nagging engine.

The principle I’d add to the canon is:

> **Importance determines what Lumi remembers. Change, consequence, and permission determine when she interrupts.**

That gives Coherence room to become genuinely proactive without quietly becoming another system the user has to defend their attention from.

I’m not producing a mockup for this exploration. This is primarily a behavioural and systems policy; a visual would prematurely imply that proactivity needs a new surface when the stronger design move is for it to flow through the existing Home, Today, Lumi bubble, and eventual notification mechanisms.
