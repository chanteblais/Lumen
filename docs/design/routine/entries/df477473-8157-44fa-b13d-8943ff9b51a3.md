Focus Together already exists, but it currently runs on **Home**: one session at a time, with a goal, first step, planned duration, elapsed-time bar, check-ins, and session-end reflection. **Start with Lumi** from Today already means “begin this,” not “open another planning dialog”: it hands the actual Right now intention and first step into Home and starts accompaniment. Study, meanwhile, is settled as a conceptual space for narrowed attention, but there is no separate Study route or implemented Study room yet.

The canon also explicitly says **not every beginning needs a formal session**. Study is supposed to narrow attention to present work, not become another module the user has to manage.

### OPEN QUESTION

**Q2 — How does Focus move into Study?**

The unresolved part is not really “what page should Study be?” It is more fundamental:

**What marks the moment when Coherence should stop helping the user orient and instead help them inhabit one piece of work?**

If Study becomes another destination in navigation, the user has to notice they need focus, decide to go somewhere, enter it, and possibly configure a session. That adds exactly the sort of transition burden Coherence is trying to remove.

### PROPOSAL — **Study should be a temporary focus state entered through commitment, not a place the user has to go find**

I would not add **Study** to the main navigation.

Instead, Study begins when the user makes an explicit commitment to stay with one thing and asks Lumi to accompany that commitment.

Today already has the right threshold:

**Start with Lumi**

That action could become the canonical doorway into Study.

The interaction would be:

**Today → Start with Lumi → Study**

with the current intention, first step, and relevant context carried through automatically. No second setup screen. No “What would you like to work on?” because Coherence already knows.

Home can enter the same state through existing behaviours such as **Body double**, **Focus Together**, or a conversational commitment:

> “Okay, stay with me while I write this.”

The important thing is that both routes produce the **same Study state**. Study is not a separate silo; it is the shared system becoming deliberately narrower.

Once entered, the information hierarchy should collapse aggressively. Study only needs to hold:

- **what I’m with**
- **the immediate threshold**
- **Lumi**
- **a quiet way out**

Everything else remains known by Coherence but leaves the foreground.

So if Today currently knows:

> Finish practicum notes  
> First: open the last client record and review the session summary.

Study should not bring along the rest of Today, the backlog, other priorities, or Library context simply because those data exist.

It should feel like:

> **We’re here now. This is enough.**

That is the cognitive function Study can uniquely provide.

### The key distinction: beginning vs. staying

I would make **Study optional even after something becomes Right now**.

Someone may look at Today, understand what to do, and simply leave Coherence to do it. That is success.

Study is useful when the user wants the system to help them **stay in contact with the intention**.

That makes the semantic distinction clean:

**Right now** answers:  
> What deserves my attention?

**Study** answers:  
> Help me stay with it.

This avoids turning every task into a timed focus session.

### The session bar should belong to the state, not the Home page

The existing elapsed-time/session controls currently live above Home’s composer because that is where Focus Together was implemented.

Directionally, I would treat that bar as a **Study-state element** instead.

It does not need to become an elaborate timer interface. Its main purpose is orientation:

> What am I doing?  
> How long have I been here?  
> Can I ask Lumi for help?  
> Can I stop?

That means the Study transition can remain very light.

When entered from Today, the user should not feel as though they opened an entirely new productivity tool. The room/state changes enough to reduce peripheral information, Lumi remains present, and the chosen work becomes dominant.

### Exiting Study should not require success

This boundary is important.

**Leaving Study is not equivalent to failing the session.**

The user should always be able to exit without classifying what happened.

If they explicitly complete something, great. If they say they got stuck, that is useful context. If they just leave, Coherence should retain an **unknown ending** rather than inventing abandonment.

That keeps this proposal compatible with Q28, which remains separately unresolved.

On an explicit end, Lumi might offer only the smallest useful next move:

> Done here  
> I’m stopping for now

and allow ordinary navigation away without selecting either.

Study should not demand a post-session report in exchange for freedom.

### Returning should preserve orientation

If the user enters Study from Today, ending it should return them to **Today**, with whatever is actually known reflected there.

If they entered through Home conversation, they return to **Home**.

That source relationship matters because Study is a temporary narrowing, not another organizational home.

Conceptually:

**Home / Today → narrow → Study → widen back**

rather than:

**Home → Study page → navigate somewhere else**

That would also make the eventual motion design meaningful: entering Study is a contraction of attention; leaving is a restoration of context.

### Why I think this is a strong fit

It removes a future navigation decision while giving Study a very clear product job.

It also creates a useful four-part rhythm across the existing spaces:

**Home:** What is going on?  
**Today:** What matters now?  
**Study:** Stay with this.  
**Library:** What else exists in my life?

Those are distinct enough to justify Study without requiring another permanent destination.

### HISTORICAL / REJECTED BOUNDARY

I would avoid turning Study into a Pomodoro dashboard, a productivity analytics space, a mandatory “deep work” mode, or another room users must maintain.

I would also avoid automatically launching Study whenever the user taps a task. Selecting or starting something does not necessarily mean they want supervision or a formal session.

The principle I would add to the design direction is:

> **Study is entered through an explicit request for accompaniment, not merely through the existence of work.**

I’m deliberately **not generating a Study mockup on this run**. The context package explicitly says there is no active-focus or Study screenshot in the current visual-reference set. I can ground the interaction proposal from the implementation and canon, but I cannot honestly claim a new Study visual is an extension of a currently pictured state. Once a real active Focus Together capture is added to the package—or Study’s visual direction is otherwise established—that would be the right moment to explore the transition visually.
