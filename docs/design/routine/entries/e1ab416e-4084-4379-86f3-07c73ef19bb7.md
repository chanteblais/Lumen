The relevant current-state limitation is fairly concrete: Lumi receives intentions, beliefs, recent activity, capacity, session state, and mail-lead context, but this is currently assembled into **one capped context block**. The broader model—Threads, richer provenance, distinct Intention/Action structures, space-specific context, retrieval beyond the cap—is direction rather than implemented reality.

At the same time, the canon already gives a strong architectural clue: Home, Today/Garden, Library, and Study are not separate little apps. They are **different cognitive views over the same shared life context**. The sequence *life → evolving model → relevant context → today → now* is supposed to be progressive selection.

That makes the current single context block a meaningful mismatch with the eventual product philosophy.

## DIRECTION

I think context should become **temporarily shaped around the place and the thing the user is doing**, rather than simply becoming a larger and smarter pile of remembered information.

The underlying shared model can be rich.

Lumi’s working context should be small.

My proposed principle is:

> **Coherence remembers broadly; Lumi attends narrowly.**

This matters because the obvious solution to better memory is to keep stuffing more into the model prompt. That would eventually make Lumi less coherent, not more: old priorities, unrelated relationships, stale task state, recent conversations, calendar changes, inferred patterns, and long-term preferences would all compete for interpretive weight.

The system needs an attentional layer between memory and Lumi.

## OPEN QUESTION

This is **Q24 — How does context selection evolve?**

The unresolved pieces include space-specific context, Study compression, retrieval beyond current caps, relevance decay, observability, and reconciliation. The current 14-day stale heuristic explicitly does **not** establish that old context is irrelevant or avoided.

I would narrow the design question to:

> **What is the smallest working representation Lumi needs for the interaction happening right now, while still allowing the rest of the person’s life to remain retrievable?**

## PROPOSAL — **Context Capsules**

For every meaningful interaction, Coherence should assemble a temporary **Context Capsule**.

A Capsule is **not another user-visible object**. The user does not create it, name it, file things into it, or clean it up.

It is simply the working set Lumi receives for this moment.

A Capsule would contain five kinds of context:

- **Anchor** — what this interaction is actually about: a current intention, Focus session, conversation topic, eventual Thread, person, commitment, or external signal.
- **Now** — immediate conditions that materially affect what happens next: Today’s current choice, capacity, time constraints, changed appointment, unfinished Focus session, etc.
- **Stable context** — explicit information that changes interpretation of the anchor: standing preference, constraint, enduring priority, relevant relationship information.
- **Delta** — what has changed since this subject was last active, rather than a replay of everything that happened.
- **Support context** — instructions relevant to how Lumi should help here: “don’t check on me unless I ask,” “challenge me when I get stuck in analysis,” or a session-scoped mandate.

Everything else remains available to retrieve, but it does not automatically occupy Lumi’s attention.

That distinction is the proposal.

## The spaces should change the Capsule, not own different memories

This gives the existing places much stronger cognitive meaning without turning them into data silos.

On **Home**, the Capsule can be relatively broad. It might include the current conversational subject, a small amount of recent continuity, explicitly relevant relationships or Threads, and meaningful changes since the last conversation. Home is where ambiguity is allowed, so the Capsule does not need to begin from a task.

On **Today**, it becomes much narrower: current plan, capacity, fixed commitments, scoped priorities, and only the context needed to understand why something belongs—or does not belong—in the foreground.

If Today is asking whether the case formulation should be Right now, Lumi does not need the user’s entire practicum history. She might need that practicum is the semester priority, the deadline moved forward, the draft is partly started, and today is low-capacity.

On **Focus Together / future Study**, compression should be strongest. The Capsule becomes almost a little working table:

> This is what we are doing.  
> This is the next threshold.  
> These are the relevant constraints.  
> This is what got in the way recently.  
> This is how the user wants me to accompany them.

That is enough.

And **Library** does something almost opposite: it helps *find* breadth, but once the user enters a particular piece of context, Lumi again forms a bounded Capsule around it.

So Library can expose a large life model without requiring the conversational model to ingest the entire Library every turn.

## Re-entry should be based on **delta**, not age

This is probably the most important part.

Suppose the user returns to a practicum-related conversation after three weeks.

A recency-oriented system asks:

> What happened in the last 14 days?

A continuity-oriented system asks:

> What changed that affects this practicum context?

Those are very different queries.

Maybe twenty unrelated things happened recently.

But for this Thread, only three facts matter:

> The supervisor replied.  
> The deadline moved.  
> The user finished the outline outside Coherence.

That is the re-entry Capsule.

This would make Lumi’s return behaviour dramatically cleaner. Instead of rereading a chunk of chronological memory and trying to rediscover the state of things, Coherence reconstructs **the current difference from the last known orientation**.

That also handles long-running subjects much better. Something can be six months old and still highly relevant because the user has intentionally returned to it.

Age can influence retrieval cost.

It should not define meaning.

## Capsules should have **anchors**, not just similarity search

I would be careful about relying too heavily on generic semantic retrieval.

If the user says:

> “Richard replied.”

similarity search might retrieve anything containing Richard, supervision, practicum, textbook work, or email.

But if the active anchor is already:

> **case formulation / practicum**

the retrieval problem becomes much easier.

So context selection should prefer known relational structure whenever available:

**current Focus goal → related intention → eventual Thread → associated people / commitments / prior conversations**

and only then use semantic retrieval to fill gaps.

This also gives the earlier **Thread** proposal a very practical payoff. Threads do not need to become a huge interface feature to be valuable. A Thread can simply become one of the strongest possible Capsule anchors.

But Capsules do **not** need to wait for Threads to ship. The first implementation could anchor on the current route, current intention/session, conversation topic, known beliefs, and recent tool state.

## Context that falls out of a Capsule is not forgotten

This is an important semantic boundary.

Removing something from Lumi’s current working set should mean:

> **not relevant enough for this interaction**

not:

> stale  
> unimportant  
> archived  
> false  
> forgotten

Those operations need to remain separate.

If the user has not mentioned wanting children for two years, that does not automatically make the information false.

It may simply have no place in a conversation about preparing tomorrow’s practicum session.

Likewise, an intention being absent from Today does not make it absent from the shared model.

The whole architecture becomes more trustworthy if **attention and retention are separate systems**.

## Consequential inferences should enter Capsules differently from explicit facts

This proposal also creates a clean place for the explicit / observed / inferred distinction.

If the user directly said:

> “Practicum is my main priority this semester.”

that can enter relevant Capsules as authoritative scoped context.

If Lumi has merely inferred:

> “You seem to be losing interest in practicum.”

that should not enter the Capsule as equivalent truth.

It might enter as a tentative hypothesis only when genuinely useful:

> *Possible interpretation: motivation around practicum may have changed.*

That provenance can remain attached internally.

If Lumi ever acts on it conversationally, she can express the uncertainty naturally rather than treating the inference as remembered fact.

This prevents context compression from quietly flattening epistemic differences.

## Capsules should be inspectable **when something goes wrong**, not continuously visible

Q24 also mentions observability. I think the temptation here would be to build a developer-like “Current Context” drawer showing everything Lumi sees.

I would avoid that as the primary experience.

Most users should never have to inspect a Capsule.

But if Lumi says something surprising:

> “Since practicum isn’t very important to you anymore…”

the user should be able to ask:

> “Why do you think that?”

And Coherence should be capable of tracing the claim:

> “You said last week that you were considering leaving the placement, and I interpreted that too broadly.”

That is useful observability.

A permanently visible memory/debug panel is system administration.

So I would build the **traceability architecture first**, and only later decide where explicit inspection belongs under Q12.

## Minimal implementation path

I would resist trying to build retrieval infrastructure, full Threads, relationship objects, relevance decay, sophisticated embeddings, and the entire shared ontology simultaneously.

A first Context Capsule can be assembled mostly from things Coherence already has:

current surface → current plan/session → relevant intention → explicit beliefs/preferences → recent changes and tool actions → limited conversational history.

Give each included item a reason such as:

> current goal  
> directly referenced  
> standing explicit instruction  
> changed since last interaction  
> strongly related to current intention

That reason does not have to be shown to the user. It creates a foundation for later observability and debugging.

Once Threads become structured, they improve anchor selection.

Once Library becomes navigable, it improves deliberate retrieval.

Once richer inference exists, provenance improves what can safely enter a Capsule.

The architecture scales without requiring all of those things now.

## HISTORICAL / REJECTED

I would reject **“better context = larger prompt.”** The shared model can eventually become enormous; Lumi should not experience the person as an ever-growing transcript.

I would also reject generic recency as the primary relevance system. “Older than fourteen days” is a useful engineering signal, not a theory of human importance.

And I would avoid duplicated space-specific memory—one memory model for Today, another for Home, another for Study. The spaces should receive **different selections from the same evolving model**, otherwise contradictions and maintenance burden will grow quickly.

The design principle I would add is:

> **Coherence maintains a broad shared model, but each interaction gives Lumi a temporary Context Capsule anchored to the user’s present concern. Context leaves attention without being forgotten; re-entry retrieves what changed, not merely what is recent.**

I’m deliberately not generating a mockup for this exploration. This proposal is the **selection architecture beneath the existing spaces**, and making it visible as a new panel or context-management screen would work against the goal. The right evidence that it has been implemented well should be that Lumi suddenly seems to remember *less at once, but the right things*.
